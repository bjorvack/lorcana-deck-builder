# Design

## Spike findings (2026-11-20, upstream `6de59de1`)

These are verified facts that shape every decision below:

- The engine runs unmodified under Node 26 + `tsx`. Package-alias resolution
  needs symlinks for the `@tcg/*` workspace names (they are `link:`/`workspace:`
  deps upstream, not published to npm); runtime npm deps are
  `@logtape/logtape`, `@logtape/pretty`, `mutative`, `nanoid`, `seedrandom`,
  `zod`. One stub was needed for `@discord/embedded-app-sdk` (imported by a
  shared rich-presence module, unused headless).
- Headless AI-vs-AI entry point: `createLorcanaServerGame(...)` then loop
  `getCurrentActorId()` → `takeAutomatedActionForCurrentActor({ strategy })`
  until `getBoard().winner` is set. Per-seat strategy objects come from
  `AUTOMATED_ACTION_STRATEGIES` (ids: `deck-aware-lore-race` (oracle),
  `best-deck-aware-lore-race` (fair-info), `best-deck-aware-oracle-lore-race`,
  `board-control-lore-race`, `aggressive-board-control-lore-race`).
- Throughput: ~242 ms/game (~4 games/s) single-threaded, 20/20 games finished,
  0 errors. 10⁴ games ≈ 40 min single-threaded.
- **Determinism trap**: `fromDeckToCardInstances` draws card instance ids from
  unseeded `Math.random()`, and the planner breaks candidate ties by
  instance-id comparison — same seed, different games. Fix (verified): re-key
  instance ids deterministically from (owner, cardId, index) before engine
  construction. The runner must own this, never upstream.
- Card data: engine canonical catalog is 3374 cards keyed `set{code}-{number}`
  (`set14-001`), each carrying `externalIds.lorcast`. Our catalog (3556
  entries) joins by `set{setCode}-{collectorNumber.zfill(3)}` at 86.4% naive
  coverage; misses are Epic-rarity printings awaiting an upstream bump,
  Quest sets (Q1–Q3), and promo/challenge key formats (`p3-023`), not core
  cards.

## Vendoring

- **Pinned checkout, not npm dependency**: the packages are `private: true`
  and npm git deps do not run their workspace resolution. Vendor the minimal
  subset into `scripts/training/vendor/lorcana/`: `lorcana-engine/src`,
  `lorcana-types/src`, `lorcana-cards/src` (data JSONs are ~16 MB — keep
  canonical + aux, drop localizations we do not use), plus the used
  `agnostic-simulator` packages (`bot-core`, `shared` card-catalog util,
  `protocol`). Record upstream commit in `vendor/PIN.md` with LICENSE +
  DISCLAIMER attribution.
- Alias strategy: commit the `@tcg/*` symlink layout as relative paths via a
  committed `package.json` in the vendor root (npm honors `file:` deps), so
  `tsx scripts/training/arena/*.ts` resolves without global state. The stub
  for `@discord/embedded-app-sdk` ships in the vendor tree with a comment.
- Engine runtime deps get added to our root `package.json` (they are plain
  npm packages) so there is no second install step.

## Card-ID mapping

- **Identity is functionality, not print** (D1, `scripts/training/canonical.ts`):
  reprints, rarities, promos and enchanted/epic variants of the same card share
  one training unit — they all alias to the group's canonical print via
  `canonicalAlias()` and inherit its data, shape and vector. Snapshot check
  (2026-11-20): 3,556 prints collapse to 2,785 identities, zero stat-level
  drift within groups; Quest challenge variants already carry distinct
  groupKeys, so differently-functioning cards never collide.
- **Resolution policy (correctness first)**: the identity resolves through its
  registry-canonical print's plain printing key (`set{n}-{num}`); a key hit is
  accepted only when the engine card's name+version matches ours (normalized to
  letters/digits — typography and stylized punctuation ignored). On a key miss
  *or* a name disagreement the resolver falls back to a normalized name+version
  index; with multiple candidates it picks by printing evidence (exact key >
  shared collector number) and refuses when ambiguous. An unresolved identity
  is **unmapped, never wrongly mapped** — the pre-hardening map silently
  pointed set 7's Moana/Vaiana (mis-numbered 026 in our snapshot, sharing the
  collector number with Calhoun) at Calhoun's engine card.
- Output: a committed mapping artifact
  (`scripts/training/arena/card-map.json`: our identity id → engine card id +
  key + resolution path + upstream `missingImplementation` flag, plus
  printing→identity alias reuse from `canonicalAlias()`) regenerated by a
  script, with coverage reported into `public/data/report.json` (per-set
  counts, ineligible categories, audited quirks).
- Drift guard in the report: any group whose members differ in cost/stats/
  ink/type (not wording — newer prints legitimately reword) is flagged
  needs-review instead of silently merging.
- Eligibility is identity-level: an identity is arena-eligible iff the engine
  can resolve it; a deck containing that identity through any printing plays
  it. Identities with no engine definition are reported as ineligible, never
  substituted.
- The map format versions the cache: remapping an identity changes the cache
  hash, so records played under the previous resolution are never reused.
- Snapshot quirks surfaced by the audit (2026-11-20 state: 2,681/2,785 mapped
  — 2,679 via key, 2 via name; 104 quest identities ineligible by design; 0
  name mismatches): `setNumber` is always 0 (setCode carries the set); three
  set-7 cards share collector number 026 in our snapshot (Calhoun base + the
  Moana/Vaiana P2 promos) — a data-pipeline needs-review; upstream ships
  separate defs for promo reprints (set7 Moana #156 vs the 026 promo) and
  flags 6 consumed cards `missingImplementation` (fidelity note in coverage).

## Runner and record format

- One JSONL line per game: `{ engineCommit, seed, decks: {p1, p2} (identity id
  → count), strategies: {p1, p2}, winner, turns, actions, fallbacks,
  loreTimeline, incomplete }` — no wall-clock fields, so identical inputs
  produce byte-identical records (the determinism test asserts this).
- Cache: `scripts/training/data/arena/{engineCommit8}/{deckPairHash}/
  {strategyA}__{strategyB}/{format}-{seedBase}-{games}.jsonl`. Same key →
  reuse; a changed engine commit never reads older eras. Determinism is
  asserted by a regression test that replays one fixture matchup twice and
  byte-compares.
- Batch CLI shape mirrors the existing source fetchers:
  `tsx scripts/training/arena/run.ts --deck <file> --opponent <file>
  --games N --strategies <id,id> [--seed-base S] [--parallel K]`.
  Parallelism uses child tsx processes (games are independent; instance-id
  keying removes cross-game nondeterminism).
- The runner imports vendor code only; `src/` never does. Vitest coverage:
  mapping (join + fallback + report), determinism replay, record schema,
  cache reuse.

## Engine lifecycle

- Bump = script-assisted: update pin → regenerate vendor subset + mapping →
  run determinism + throughput checks → coverage delta in the validation
  report → training gates re-run on next training invocation. Cache keys make
  the transition clean; the miner stratifies records by engine version.

## Alternatives considered

- **InkTable automation**: closed-source client-side app, human-vs-AI only, no
  API; Playwright-driving it would occupy the human seat (our-bot vs their
  heuristic AI), not AI-vs-AI, and would burden an ad-supported solo-dev
  site. Rejected as an integration target; kept as manual QA.
- **ngroover/lorcana** (Python): capable but unlicensed — legally
  unbuildable-on, plus stack mismatch.
- **Extending our goldfish**: the goldfish is deliberately one-sided against
  scripted baselines; a full two-sided engine for ~3.5k cards' effects is a
  multi-month build when an MIT one exists.
- **Engine fallback card definitions for unknown cards**: rejected — silent
  placeholder games would corrupt every downstream statistic.
